### Phase 62：HNSW 图结构直接 RDB 序列化（`kSearchEncVer = 14`）

#### 问题背景
当前 `RdbSaveSearch` 只保存 `DocumentStore` 中的原始文档字段，重启时 `RdbLoadSearch` 逐条调用 `AddDocumentToIndex` 重新构建所有索引。对于 `HnswIndex`，单线程 $O(N \log N)$ 重插建图在十万/百万级向量下会导致重启耗时数分钟。

#### 核心设计
1. **`HnswIndex` 纯内存序列化/反序列化接口**（`modules/gemini-search/src/hnsw_index.h` / `hnsw_index.cc`，不依赖 `redismodule.h`）：
   - 新增结构化序列化回调或字节流接口（`SerializeGraph(Writer)` / `DeserializeGraph(Reader)`），按紧凑二进制格式读写：
     - Header：`magic`、`version`、`dim`、`metric`、`quantization`、`m`、`m_max0`、`ef_construction`、`ef_runtime`、`entry_point`、`max_level`、`live_count`、`num_nodes`
     - 节点表（仅写出紧凑化后的活节点，或在保留槽位 ID 时写出 `alive` 位图；推荐**保存时按活节点紧凑重编号 `0..live_count-1`**，同步重映射 `entry_point` 和邻接表 ID，既去除了墓碑碎片又减小 RDB 体积）：
       - 每个活节点：`doc_id`、`max_layer`、量化/原始向量数据（`kNone` 写 `dim * float`、`kSq8` 写 `Sq8Meta + dim * uint8`、`kBq` 写 `bq_words * uint64`）
       - 每层邻接表：`layer = 0..max_layer`，写 `deg` (`uint16_t`) + `deg` 个 `uint32_t` 邻居 ID
   - 反序列化严格校验（防恶意/损坏 RDB）：
     - 校验 `dim` / `metric` / `quantization` 与 `IndexSpec` 一致；
     - 校验 `num_nodes <= kMaxNodes`、`max_level <= 64`、`entry_point < num_nodes`（非空时）；
     - 校验每层 `deg <= (layer == 0 ? m_max0 : m)` 且所有邻居 ID `< num_nodes` 且无自环；
     - 校验 `doc_id` 唯一性，构建 `id_to_node_`；
     - 任意校验失败返回 `false`，绝不崩溃或 OOM。
2. **RDB `kSearchEncVer = 14` 集成**（`modules/gemini-search/src/search_rdb.h` / `search_rdb.cc`）：
   - 升级 `kSearchEncVer = 14`，完全向后兼容 `encver 1..13`（旧版仍走原重建逻辑）。
   - `RdbSaveSearch` 在写完 `IndexSpec` 与 `DocumentStore` 后，为每个 `ALGORITHM HNSW` 向量字段写出序列化图块（`field_name` + 图数据）。
   - `RdbLoadSearch`（`encver >= 14`）先重建非 HNSW 索引（Text/Tag/Numeric/Geo/Flat），对 HNSW 字段直接调用 `HnswIndex::DeserializeGraph` 恢复图结构；若图块缺失则安全回退到从 `DocumentStore` 重建。
3. **验证与基准**：
   - **GTest + ASan/UBSan**（`hnsw_index_test.cc`、`search_rdb_test.cc`）：
     - 覆盖 `FP32` / `SQ8` / `BQ` 三种量化模式 + `L2`/`COSINE`/`IP` + 删除后含墓碑节点的紧凑序列化往返；
     - 验证反序列化后 KNN-10 结果与保存前 **100% 一致**；
     - 字节级截断与随机篡改 Fuzz 测试，要求优雅返回失败、零泄漏、零崩溃。
   - **`search_bench`**：新增 `HnswIndex RDB Save/Load vs Rebuild (5k × 128d / 2k × 768d)` 对比指标。
   - **Tcl 集成测试**：`BGSAVE` + 重启 + `PSYNC` 主从全量同步下验证 HNSW `FP32`/`SQ8`/`BQ` 查询一致性。

### Phase 63：BQ 两阶段检索（Oversample & Rerank）

#### 问题背景
`QUANTIZATION BQ` 提供 32× 内存压缩与 `~7.5 us` 极速查询，但 1-bit 符号量化在高维语义向量（768d/1536d）下 Top-10 召回率通常只有 60%–80%。引入可选的两阶段检索（BQ 粗排取 `k * oversample` 候选 + 紧凑精排向量重算精确距离）可在远低于 FP32 的内存开销下将召回率拉升至 95%+。

#### 核心设计
1. **Schema 与存储设计**（`index_spec.h`、`vector_index.h/cc`、`hnsw_index.h/cc`）：
   - 扩展 `VectorFieldParams`：
     - `VectorQuantization` 保持 `kNone / kSq8 / kBq`，新增可选精排存储模式 `VectorRerankType { kNone, kFp16, kSq8 }`（`FT.CREATE ... VECTOR ... QUANTIZATION BQ RERANK FP16` 或 `RERANK SQ8`，默认 `NONE` 保持 100% 向后兼容）。
     - 默认过采样倍率 `size_t bq_oversample = 4`（可在 `FT.CREATE` 通过 `OVERSAMPLE <n>` 配置，也可在查询侧 `PARAMS` 或 `FT.SEARCH` KNN 语法中按次覆盖，如 `KNN 10 @vec $blob OVERSAMPLE 8`）。
   - 存储布局：
     - 当 `quantization == kBq && rerank != kNone` 时，除保存 `bq_vectors_`（1 bit/dim）外，额外在稠密数组中保存一份 `fp16_vectors_`（`uint16_t`，2× 压缩）或 `sq8_vectors_ + sq8_meta_`（4× 压缩）。
     - HNSW 图遍历与 `FlatVectorIndex` 第一阶段扫描仍完全使用 **BQ 汉明距离**（保持 SIMD `vcntq_u8`/`popcnt` 极速）；
     - 粗排产出 `cand_k = min(size, k * oversample)` 个候选后，第二阶段仅对这 `cand_k` 个节点用 `fp16` 或 `sq8` 精确距离重排并截断取 Top-K。
2. **持久化与观测同步**：
   - `search_rdb.cc`（在 `encver 14` 中一并持久化 `rerank` 与 `bq_oversample`，或单独保留字段位）、`AofRewriteSearch` 补齐 `RERANK` / `OVERSAMPLE` 输出。
   - `FT.INFO` 与 `SearchMemUsage2` 准确反映精排向量内存占用。
3. **验证与基准**：
   - **GTest（召回率 + 正确性）**：构造 5k × 768d 归一化随机/聚类向量集，对比：
     - `Flat FP32`（Ground Truth，Recall@10 = 100%）
     - `HNSW BQ`（纯 BQ）
     - `HNSW BQ + RERANK SQ8 (OVERSAMPLE 4/8)`
     - `HNSW BQ + RERANK FP16 (OVERSAMPLE 4/8)`
     验证两阶段检索在 768d 下 Recall@10 显著跃升（目标 ≥ 95%）且查询延迟远低于 FP32。
   - **ASan/UBSan + Tcl**：覆盖 `FT.CREATE` / `FT.SEARCH` / `FT.HYBRID` / `BGSAVE` / AOF 重写 / `PSYNC`。

### Phase 64：`FT.CREATE` 后台增量异步建索引（Background Indexing）

#### 问题背景
当前 `FT.CREATE`（无 `SKIPINITIALSCAN` 时）在 `search_index_cmds.cc:414` 同步调用 `ScanExistingKeys(ctx, index)`，一次性扫描整个 Redis keyspace 并建完所有索引后才返回 `OK`。当库内有几十万/百万个 Hash 或 JSON key 时，主线程会被长时间阻塞。

#### 核心设计（Redis 7 Timer + ScanCursor 时间片机制）
> 为什么采用 `RedisModule_CreateTimer` + `RedisModule_ScanCursor` 而不是纯后台线程直接读 keyspace？
> Redis keyspace 访问必须持有主线程 GIL；时间片增量扫描在主线程每次仅推进少量 key（例如每 tick 最多处理 128 个 key 或耗时 ≤ 2ms），无需跨线程锁竞争，天然兼容 `ON HASH` 和 `ON JSON`，且与 `BGSAVE`/复制/keyspace 事件语义完全一致。

1. **增量建索引状态机**（`search_internal.h`、`search_keyspace.cc`、`search_index_cmds.cc`）：
   - 在 `SearchIndex` 上新增状态字段：
     - `bool indexing = false;`（是否正在后台建索引）
     - `uint64_t total_scan_keys = 0;` / `uint64_t scanned_keys = 0;` / `double percent_indexed = 1.0;`
     - `RedisModuleScanCursor* scan_cursor = nullptr;`
     - `RedisModuleTimerID scan_timer_id = 0;`
     - `uint64_t index_generation = 0;`（防 timer 触发时索引已被 `FT.DROPINDEX` 删除或重建的 ABA 问题）
   - **触发条件与配置**（`FT.CONFIG`）：
     - 新增配置项 `BG_INDEX_MIN_KEYS`（默认例如 `1000`，当 DB key 总数 `RedisModule_DbSize(ctx) >= BG_INDEX_MIN_KEYS` 时自动走后台增量建索引；小库仍同步完成，零延迟且不影响现有小规模单测），以及 `BG_INDEX_BATCH_KEYS`（默认 `128`）、`BG_INDEX_TICK_MS`（默认 `1` ms）。
     - 支持 `FT.CONFIG SET BG_INDEX_MIN_KEYS 0` 在测试中强制走后台路径。
   - **Timer 回调流程**：
     - 每次 tick 用 `index_name + generation` 查表确认索引仍存活；
     - 调用 `RedisModule_Scan(ctx, cursor, ...)` 处理至多 `BG_INDEX_BATCH_KEYS` 个 key（同时受单 tick 时间预算 ≤ 2ms 约束）；
     - 写索引时获取该索引的 per-index `unique_lock`（与并发异步查询的 `shared_lock` 安全互斥）；
     - 扫描完成时释放 `scan_cursor`，置 `indexing = false`、`percent_indexed = 1.0`；未完成则重新调度下一次 timer。
2. **并发与生命周期安全边界**：
   - **建索引期间的实时写事件**：Keyspace 通知对匹配前缀的新增/修改/删除正常生效，幂等更新（`UpdateDocument` 覆盖旧版本），避免遗漏热写。
   - **建索引期间的查询**：允许查询已建好的部分文档（与 RediSearch 公开行为一致），且受 per-index `shared_mutex` 保护不会数据竞争。
   - **`FT.DROPINDEX` / `FLUSHDB` / `FLUSHALL` / 模块卸载**：立即 `RedisModule_StopTimer` + `RedisModule_ScanCursorDestroy` 清理游标与状态，防止悬空指针与内存泄漏。
   - **`FT.INFO` 观测**：输出 `indexing`（`0` 或 `1`）与 `percent_indexed`（`"0.00"` ~ `"1.00"`）。
3. **验证与压测**：
   - **Tcl 集成测试**：
     - 预置 5,000 个 Hash / JSON key，设置 `BG_INDEX_MIN_KEYS 0`，执行 `FT.CREATE` 立即返回 `OK`；
     - 建索引过程中并发执行 `PING` / `SET` / `HSET` / `DEL` / `FT.SEARCH` / `FT.INFO`（观测 `indexing` 从 `1` 变为 `0`、`percent_indexed` 到达 `1`）；
     - 验证建索引中途执行 `FT.DROPINDEX` 与 `FLUSHDB` 零崩溃、零泄漏；
     - 验证最终文档数与同步建索引 100% 一致。
   - **ASan + Soak**：在 Docker Redis 7.2 中运行包含后台建索引的回归测试。

## Track C：主流客户端 SDK 端到端兼容测试（`redis-py`）

### 背景与目标
`Dockerfile.redis7` 已预装 `redis`（`redis-py`），但目前 CI 脚本主要用 Tcl 和底层 `execute_command` 测试。实际用户调用 `r.bf()`、`r.cf()`、`r.cms()`、`r.topk()`、`r.tdigest()`、`r.json()`、`r.ft()` 时，`redis-py` 会按严格格式解析返回数组/Map（如 `FT.INFO` 键值对、`FT.SEARCH` 文档结构、`FT.AGGREGATE` 行、`JSON.GET` JSON 反序列化、`BF.INFO` 字段名）。

### 实施内容
1. **新增测试套件**：`ci/sdk_compat_test.py`
   - 启动加载全部 3 个模块（`redis_bloom.so` + `redis_json.so` + `redis_search.so`）的 Redis 7.2 实例，分别在 **RESP2** 和 **RESP3** 下用 `redis-py` 高层 API 执行全链路测试：
     - **Bloom / CF / CMS / Top-K / T-Digest**：`r.bf().reserve/add/madd/exists/mexists/info/card/scandump/loadchunk`、`r.cf().*`、`r.cms().*`、`r.topk().*`、`r.tdigest().*`（含 `quantile`/`cdf`/`rank`/`trimmed_mean`/`info`）。
     - **JSON**：`r.json().set/get/mget/arrappend/arrpop/numincrby/objkeys/merge/delete/type/clear/toggle` + RFC 9535 filter 路径。
     - **Search**：`r.ft("idx").create_index(...)`（`ON HASH` 与 `ON JSON`）、`search(Query(...).paging(...).highlight(...).summarize(...).sort_by(...))`、向量 KNN 查询（`FLAT` / `HNSW` / `SQ8` / `BQ`）、`aggregate(AggregateRequest(...).group_by(...).sort_by(...))`、`info()`、`sugadd/sugget`、`spellcheck`、`aliasadd/aliasupdate`、`tagvals`。
   - 对运行中暴露出的任何 RESP2/RESP3 字段名、类型或结构不匹配问题，逐项在模块命令层修复并补充对应 Tcl 用例。
2. **接入 CI**：
   - 在 `ci/run_tests.sh` 中增加 `SDK Compat (redis-py, RESP2 & RESP3)` 阶段，确保后续每个 PR 都自动回归。
